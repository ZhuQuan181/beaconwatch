BeaconWatch is a working Remote ID (RID) receiver and airspace dashboard. It
decodes ASTM F3411 / Open Drone ID broadcasts from Wi-Fi Beacon, Wi-Fi NAN and
BLE, queues observations on the edge, ingests them over MQTT, stores them in
TimescaleDB, and renders live and historical traffic on a MapLibre dashboard.

The protocol tests use complete frames generated by the upstream
[OpenDroneID C encoder](https://github.com/opendroneid/opendroneid-core-c), not
hand-built payloads.

The public demo is a static build with simulated traffic. The commands below
run the real edge/MQTT/database/API stack.

## What Is Implemented

- **Real ODID transport parsing:** Wi-Fi Beacon vendor IE (`FA:0B:BC`), Wi-Fi
  NAN action frames, BLE service data (`0xFFFA`), standard Message Packs and
  Basic ID / Location / Self-ID / System / Operator ID messages.
- **Reliable edge delivery:** SQLite outbox, QoS 0/1/2 publishing, PUBACK/PUBCOMP
  waits, re-queueing when the broker does not confirm a message, and supervised
  receivers that restart with bounded backoff.
- **Server ingest:** MQTT observation and station-heartbeat topics, schema
  validation, duplicate-safe idempotent writes, TimescaleDB hypertable and
  indexed keyset pagination.
- **Operations:** optional Bearer-token auth, request IDs, security headers,
  gzip, live/ready health checks, Prometheus text metrics, automatic Alembic
  migrations in the server container.
- **Dashboard:** heartbeat-monitored live WebSocket feed, timeout/retry-aware
  HTTP client, replay timeline, stations and coverage, geofences, alerts,
  unidentified-drone highlighting.
- **Verified chain:** official radio bytes → receiver → pipeline → MQTT →
  subscriber → database → HTTP, covered by unit, contract and E2E tests.

## Components

- `edge/` — async Wi-Fi/BLE receivers, Open Drone ID parser, station heartbeat,
  and reliable MQTT publisher.
- `server/` — FastAPI, MQTT subscriber, SQLAlchemy/Alembic, TimescaleDB,
  REST/WebSocket API and alert rules.
- `frontend/` — React 18, TypeScript, Vite, MapLibre GL dashboard.
- `scripts/e2e_chain.py` — real broker/database/API verification using official
  encoder output.

## Quick Start

Requirements: Docker with Compose, Python 3.11+, `uv`, and Node.js 20.19+.

```bash
make install                 # create .venv and install Python/frontend deps
make up                      # TimescaleDB + EMQX + server, with migrations
make e2e                     # real official-frame -> DB -> HTTP verification

cd frontend
npm run dev                  # http://localhost:5173
```

API documentation is at http://localhost:8000/docs and metrics are at
http://localhost:8000/metrics. EMQX's local dashboard is at
http://localhost:18083.

For a private deployment, set `RID_API_TOKEN` on the server and build the
dashboard with the same value in `VITE_API_TOKEN`. The build-time token is
embedded in the browser bundle, so use an HTTPS reverse proxy (or an
identity-aware gateway) rather than publishing that bundle to untrusted users.

## Testing

```bash
make test        # edge, server and cross-package contract tests
make lint        # Ruff + frontend typecheck
cd frontend && npm audit --omit=dev && npm run build
```

The E2E command expects the stack from `make up`. See
`docs/03-testing.md` for the full test matrix and fixture provenance.

## Production Boundaries

The Docker Compose file is a development/reference topology, not a hardened
production deployment. The API now supports optional Bearer authentication and
the MQTT subscriber supports verified TLS, but before exposing the stack to an
untrusted network you still need:

- authorization/roles, auditing and token rotation beyond the single shared
  Bearer token;
- MQTT TLS deployment, per-station credentials and ACLs;
- HTTPS/WSS termination at a reverse proxy;
- secret management and non-default database credentials;
- a shared WebSocket fan-out layer if running multiple server replicas;
- alert persistence and an operator acknowledgement/audit workflow.

The current WebSocket fan-out is in-process, so a multi-replica server requires
a shared bus such as Redis/NATS. See `docs/01-architecture.md` and
`docs/02-deployment.md` for the exact implemented topology.
