BeaconWatch is a working Remote ID (RID) receiver and airspace dashboard. It
decodes ASTM F3411 / Open Drone ID broadcasts from Wi-Fi Beacon, Wi-Fi NAN and
BLE, queues observations on the edge, ingests them over MQTT, stores them in
TimescaleDB, and renders live and historical traffic on a MapLibre dashboard.

The protocol tests use complete frames generated by the upstream
[OpenDroneID C encoder](https://github.com/opendroneid/opendroneid-core-c), not
hand-built payloads.

## What Is Implemented

- **Real ODID transport parsing:** Wi-Fi Beacon vendor IE (`FA:0B:BC`), Wi-Fi
  NAN action frames, BLE service data (`0xFFFA`), standard Message Packs and
  Basic ID / Location / Self-ID / System / Operator ID messages.
- **Reliable edge delivery:** SQLite outbox, QoS 0/1/2 publishing, PUBACK/PUBCOMP
  waits, re-queueing when the broker does not confirm a message, and supervised
  receivers that restart with bounded backoff.
- **Server ingest:** MQTT observation and station-heartbeat topics, schema
  validation, duplicate-safe idempotent writes, TimescaleDB hypertable and
  indexed keyset pagination.
- **Operations:** named API-key identities, viewer/operator/admin RBAC,
  reloadable key rotation, immutable alert and security audit records,
  request IDs, security headers, gzip, live/ready health checks, Prometheus
  text metrics, optional Redis-backed multi-replica fan-out and automatic
  Alembic migrations in the server container.
- **Alert workflow:** durable open/acknowledged/resolved state machine,
  automatic recurrence reopening, operator resolution and reopen actions,
  immutable audit events, status/rule/drone filters, live WebSocket updates,
  keyset-paginated history, aggregate statistics and opt-in retention cleanup.
- **Durable notifications:** alert lifecycle transitions are written to a
  transactional outbox and delivered by a background worker as HMAC-SHA256
  signed webhooks, with leases, bounded exponential backoff, dead-lettering
  and `delivery_id` idempotency for at-least-once delivery.
- **Dashboard:** heartbeat-monitored live WebSocket feed, timeout/retry-aware
  HTTP client, replay timeline, stations and coverage, geofences, alerts,
  unidentified-drone highlighting.
- **Verified chain:** official radio bytes → receiver → pipeline → MQTT →
  subscriber → database → HTTP, covered by unit, contract and E2E tests.
- **Horizontal scale path:** optional MQTT shared subscriptions avoid
  duplicate ingest, Redis Pub/Sub fans live frames to every API replica, and
  PostgreSQL-backed alert deduplication prevents duplicate alerts and
  notifications across workers.

## Components

- `edge/` — async Wi-Fi/BLE receivers, Open Drone ID parser, station heartbeat,
  and reliable MQTT publisher.
- `server/` — FastAPI, MQTT subscriber, SQLAlchemy/Alembic, TimescaleDB,
  REST/WebSocket API and alert rules.
- `frontend/` — React 18, TypeScript, Vite, MapLibre GL dashboard.
- `scripts/e2e_chain.py` — real broker/database/API verification using official
  encoder output.

## Quick Start

Requirements: Docker with Compose, Python 3.11+, `uv`, and Node.js 20.19+.

```bash
make install                 # create .venv and install Python/frontend deps
make up                      # TimescaleDB + EMQX + Redis + server, with migrations
make e2e                     # real official-frame -> DB -> HTTP verification
make e2e-multi               # two API replicas + Redis + MQTT shared group

cd frontend
npm run dev                  # http://localhost:5173
```

API documentation is at http://localhost:8000/docs and metrics are at
http://localhost:8000/metrics. EMQX's local dashboard is at
http://localhost:18083.

For a private deployment, generate named keys with
`python scripts/generate_api_key.py` and mount the resulting JSON file through
`RID_AUTH_USERS_FILE`. Build the dashboard with one of those keys in
`VITE_API_TOKEN`; use a read-only viewer key for wall displays. The key is
embedded in the browser bundle, so terminate HTTPS and do not publish an
operator/admin bundle to untrusted users. The legacy `RID_API_TOKEN` remains
available as a single administrator credential.

To enable alert webhooks, set both `RID_NOTIFY_WEBHOOK_URL` and
`RID_NOTIFY_WEBHOOK_SECRET`. The receiver must verify the
`X-BeaconWatch-Signature` header and de-duplicate on `X-BeaconWatch-Delivery`;
see `docs/02-deployment.md` for the signing contract.

## Testing

```bash
make test        # edge, server and cross-package contract tests
make lint        # Ruff + frontend typecheck
cd frontend && npm audit --omit=dev && npm run build
```

The E2E command expects the stack from `make up`. See
`docs/03-testing.md` for the full test matrix and fixture provenance.

## Production Boundaries

The Docker Compose file is a development/reference topology, not a hardened
production deployment. The API supports named API keys, role enforcement,
reloadable rotation, an immutable audit trail, Redis-backed multi-replica live
fan-out, and verified MQTT TLS. Before exposing the stack to an untrusted
network you still need:

- MQTT TLS deployment, per-station credentials and ACLs;
- HTTPS/WSS termination at a reverse proxy;
- an external identity provider/OIDC and multi-factor login if human accounts
  must be centrally managed;
- secret management and non-default database credentials;
- Redis ACL/TLS, high availability, capacity testing and failure drills;
- a WebSocket-capable load balancer and one MQTT shared group for replicas;
- alert retention/archive policy appropriate for your compliance regime.

Single-process deployments use in-memory fan-out by default. Multi-replica
deployments set `RID_BUS_BACKEND=redis` and `RID_MQTT_SHARED_GROUP`; see
`docs/01-architecture.md` and `docs/02-deployment.md` for the implemented
topology and failure semantics.
